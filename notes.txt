`scripts/classify_instance.py` takes a normalized SWE-bench-style `jsonl` file, validates the input/output paths, chooses the best available device (`MPS`, then `CUDA`, then `CPU`), and uses the pretrained `rafaelkallis/tickettagger-roberta` classifier to assign one label per instance. Its core pipeline is intentionally narrow: it reads only `problem_statement`, splits it into a first-line title and remaining body, normalizes function signatures, issue IDs, punctuation, non-ASCII characters, and whitespace, then rebuilds the text as a `TITLE ... BODY ...` sequence under an explicit token budget before batching it through the tokenizer and model. The script writes an atomic classification file containing only `instance_id` and `class`, and then re-reads the original source file to export a second `jsonl` that preserves the full rows for instances predicted as `feature`; with `--export-feature-only`, it can skip inference and reuse an existing classification file. The design tradeoff is clarity and reproducibility over richer modeling: it deliberately ignores repository metadata, patches, and historical context, sticks to hard labels rather than confidence-driven post-processing, and uses simple atomic writes and strict validation so the script behaves like a stable filtering stage rather than a research-heavy ranking system.

`scripts/extract_ground_truth_from_patch.py` enriches the feature-only `jsonl` by deriving structured ground truth from each row's `repo`, `base_commit`, and `patch`. It parses unified diffs with `python-unidiff`, normalizes source/target paths so renames are handled correctly, skips non-Python-like files (`.py`, `.pyi`, `.pyx`), and distinguishes file-level cases such as new files, removed files, and unsupported diff forms. For files that need scope resolution, it downloads the base version from `raw.githubusercontent.com`, caches it both on disk and in memory, replays the hunks to reconstruct the patched file, builds symbol indexes from `AST` when possible and falls back to indentation-based analysis when syntax prevents that, then maps added or changed lines to module/class/function scopes. The script treats explicit added/removed `class` and `def` headers as direct events, uses more generic changed lines to recover edited scopes when no header changed, propagates edits upward to ancestor classes, and finally writes `ground_truth`, `ground_truth_certainty`, and `ground_truth_certainty_reasons` back into each row with atomic output plus summary statistics. The design tradeoff is robustness over perfect granularity: it limits itself to Python-like files and module/class/function-level truth, prefers returning partial but traceable annotations instead of failing hard on difficult patches, and explicitly marks uncertainty when source lookup fails, patch context does not replay cleanly, AST parsing falls back to indentation, or scope resolution cannot be trusted.

We used the RoBERTa baseline from the NLBSE’23 issue report classification benchmark to classify SWE-Gym problem statements into issue types. Instances predicted as feature were mapped to feature_request; all other categories were mapped to non_feature_request. To reduce filtering noise, we retained only high-confidence predictions for the main evaluation.

For manual validation of the issue classification results, we use a stratified random sampling strategy consisting of 80 instances predicted as feature and 30 instances predicted as non-feature. The larger sample from the feature subset is motivated by our primary goal of estimating the purity (precision) of the feature-request subset used in downstream DaLIC experiments. Since the classifier is used for dataset filtering rather than as a standalone research contribution, precision of the retained feature-oriented subset is more important than maximizing recall. The smaller non-feature sample is used as a lightweight sanity check for obvious false negatives. Using 80 feature samples provides a reasonable tradeoff between manual inspection cost and statistical stability: assuming an observed precision around 90%, the corresponding 95% Wilson confidence interval is approximately 81.5%–94.8%, which is sufficiently narrow for dataset construction validation purposes.

`scripts/generate_sr_scripts.py` implements a minimum-viable, best-effort pipeline for turning each feature-class SWE-bench instance into two plain-text software-reconnaissance scripts, `script_A` and `script_B`, where `script_A = PASS_TO_PASS + FAIL_TO_PASS` and `script_B = PASS_TO_PASS`. A key design constraint is that the `PASS_TO_PASS` and `FAIL_TO_PASS` fields contain only test identifiers rather than executable workflows, so the generator must recover the underlying test source before it can remove oracles and preserve control flow. The script therefore treats these fields as test locators, not as scripts: it first normalizes each identifier, handling full `pytest` node ids, unittest-style labels, bare qualified names, and bare test names; then it builds candidate test-file paths from any explicit file paths in the identifiers and from Python files mentioned in `test_patch`; finally it loads the corresponding source from the local cache or, when missing, from the repository snapshot identified by `repo + base_commit + file_path`. Once a candidate test module is available, the script parses it with `AST`, resolves the referenced test function or test method when possible, and statically reconstructs a runnable call target. Parameterized tests are supported only through conservative heuristics: static `list`/`tuple` cases, `pytest.param(...)`, `zip(...)`, static `ids=[...]`, and a shallow layer of module-level name binding. If the script cannot unambiguously identify the target, cannot match a parameterized case id, or encounters required runtime-only parameters such as unresolved fixtures, it does not guess; instead, it records an unresolved placeholder in the generated workflow so the row remains reproducible and inspectable.

The corresponding oracle-stripping stage is also intentionally heuristic and syntax-driven rather than framework-complete. The generator clones only the imports, module-level helpers, and selected test bodies needed for the chosen workflows, removes decorators from retained tests, and then rewrites the bodies using `AST` transformations. Native `assert` statements are dropped outright; common assertion helper calls such as `self.assert*`, `fail`, and `pytest.fail` are removed by name-based matching; and expectation-oriented contexts such as `pytest.raises(...)`, `assertRaises(...)`, `assertRaisesRegex(...)`, `pytest.warns(...)`, and similar patterns are rewritten into `try/except: pass` forms so the feature-invoking body is preserved while the oracle is discarded. This means the generated scripts aim to preserve test setup structure, helper usage, and feature-triggering call sequences, but they do not claim to preserve the full semantics of the original test harness. The guiding principle is to prefer partial but traceable workflows over brittle over-synthesis: when static recovery is reliable, emit an executable skeleton that mirrors the original test's workflow; when recovery is ambiguous, emit an explicit no-op placeholder rather than inventing control flow or parameter values that cannot be justified from the base snapshot.


We construct bounded execution contrast scenarios using developer-authored test changes instead of attempting to recover full semantic feature boundaries. For each SWE-bench instance, we first identify tests associated with the test_patch, prioritising tests listed in FAIL_TO_PASS when they can be reliably mapped to executable test targets. These tests form the patch-relevant execution set (A). To construct the baseline execution set (B), we select unmodified tests from the same test file, test class, or test module that are not modified by the test_patch, prioritising nearby tests to maximise contextual similarity while avoiding direct overlap with A. To control execution cost and ensure scalability, both A and B are bounded to at most k tests per instance. We then execute A and B separately and compute Software Reconnaissance-style execution differences between their traces to derive patch-relevant execution evidence for downstream localization.
When converting selected tests into executable tracing scripts, we remove test oracles and keep only the execution-driving part of each test, including setup, input construction, and calls to the target program. Assertions and expected-output checks are removed because the goal is to collect execution behaviour rather than validate correctness. For exception-based tests, we preserve the target call inside a try-except block to avoid prematurely terminating trace collection while retaining the behavior-triggering execution.

Update: the current `scripts/generate_sr_scripts.py` is no longer driven by `PASS_TO_PASS` and `FAIL_TO_PASS`. It is now `test_patch`-driven: for each instance, it replays the `test_patch` onto the cached base test source, parses the patched Python test modules with `AST`, selects patch-relevant tests for `script_A`, selects nearby unmodified tests for `script_B`, strips oracles, and writes `script_A`, `script_B`, and `A_B_Reliability` back into `dataset/swebench_feature_with_truth_sr_scripts.jsonl`. The script still uses `tqdm` progress reporting and keeps the same default output path.

`A_B_Reliability` is assigned by the highest satisfied reliability level. Because not every instance reaches even the weakest usable level, the implementation also emits a fallback value, `0. 未达到第1级：缺少直接 test-body 锚点或 A/B 为空`, so every row has an explicit status instead of an implicit missing value. On the current `dataset/swebench_feature_with_truth.jsonl` (592 instances), the exclusive counts written by the current script are: level 4 = 68, level 3 = 308, level 2 = 33, level 1 = 160, level 0 fallback = 23. These counts depend on the current dataset and local source cache; if either changes, the distribution can shift.

Level 1 means `有直接 test-body 锚点，而且 A/B 都能生成非空`. This is the weakest still-useful level for downstream experiments. Its main value is that the instance has at least one direct test-body anchor in `test_patch`, so the generator is not building `A` purely from helper-only guesswork, and both sides of the contrast exist. For downstream tracing, this is usually enough if approximate A/B is acceptable. The remaining risks are that some workflows may still be unresolved placeholders, some arguments may still be approximated by fixture stubs, and the patch may still contain helper, import, fixture, or non-Python asset changes that make the eventual `A-B` contrast noisy rather than clean.

Level 2 adds `生成出来的 A/B 里没有 unresolved 占位 workflow`. This removes a major practical failure mode: no workflow slot in `A` or `B` is reduced to a comment plus `return None`. In downstream experiments, this matters because unresolved placeholders consume the per-instance workflow budget without contributing execution, making the contrast weaker and less predictable. Compared with level 1, level 2 is much more reliable as an execution workload, even though it may still rely on fixture stubs or include extra non-test changes.

Level 3 is the high-confidence group. Its definition is: `A`'s selected tests directly overlap changed `test_patch` lines, `test_patch` does not touch non-`.py` test assets, `A/B` contain no unresolved workflows, `A/B` do not rely on simplified runtime fixture stubs such as `_sr_tmpdir()` or `_sr_monkeypatch()`, and both `A` and `B` are non-empty. The downstream impact of the whole group is that the execution contrast is not only runnable but also more semantically aligned with the developer-written test change. The five subconditions matter for different reasons:

`A` directly overlaps changed test-body lines rather than using the nearest-test fallback. This is the most important semantic condition. It makes `A` much more likely to exercise the feature-relevant path that motivated the test change, instead of merely executing something nearby in the same module.

`test_patch` does not touch non-`.py` test assets. This reduces environment-side noise from changed golden files, text fixtures, JSON fixtures, or other test resources that could otherwise alter both `A` and `B` in ways that are only weakly related to the feature path we want to contrast.

`A/B` contain no unresolved workflows. This protects effective workload size and reduces silent no-op workflows, so the collected traces better reflect the intended number of selected tests.

`A/B` do not rely on fixture stubs. This improves fidelity to the original test harness because the workflow is executed with statically recovered arguments rather than a simplified runtime replacement for `tmpdir`, `tmp_path`, `monkeypatch`, and similar fixtures.

`A/B` are both non-empty. This is the minimum requirement for a valid contrast. Without a non-empty `A`, there is no feature-side workload; without a non-empty `B`, there is no control-side workload.

Level 4 is the cleanest subset: `patch 非常干净，只改直接 test body，不带任何额外 non-test 变动`. This means the entire `test_patch` stays inside directly overlapping Python test bodies and does not drag along helper, import, fixture, module-level, or non-Python test-asset edits. In downstream experiments, level 4 gives the purest approximation to a Software Reconnaissance-style contrast because the difference between `A` and `B` is least likely to be diluted by shared test-harness changes. The tradeoff is coverage: this level is much smaller than levels 1-3, so using only level 4 would maximize purity but substantially reduce the number of usable instances.

Compact summary of the current `scripts/generate_sr_scripts.py` A/B generation logic: for each SWE-bench instance, the script first parses `test_patch` as a unified diff, keeps every touched file for reliability analysis, and keeps touched Python test files as candidates for script generation. For each touched Python test file, it loads the base snapshot from the local cache or the repository snapshot, reapplies the `test_patch` hunks to reconstruct the patched test module, and parses the patched file with `AST`. It then identifies all test definitions in that patched module and marks which tests directly overlap changed patch lines. `script_A` is built from those directly overlapping tests; if a touched test module has no direct overlap, the script falls back to the nearest test in source order so the instance can still produce an approximate feature-side workflow. `script_B` is built from unmodified tests in the same file, preferring the same class and nearby line numbers so that `B` stays structurally similar to `A` while avoiding the modified tests themselves.

After test selection, the script statically expands parameterized tests when possible, injects a small set of simplified runtime fixture replacements such as `_sr_tmpdir()` and `_sr_monkeypatch()` when needed, and emits an explicit unresolved placeholder only when required parameters still cannot be reconstructed. It then clones the minimum module slice needed for the selected workflows, strips decorators from retained test functions, removes assertions and other oracle code, rewrites expected-failure contexts like `pytest.raises(...)` into `try/except: pass`, and renders each selected workflow as a plain Python function inside `script_A` or `script_B`. Finally, it writes `script_A`, `script_B`, and `A_B_Reliability` back to the output jsonl, where `A_B_Reliability` summarizes how cleanly and confidently the instance's A/B contrast was recovered from `test_patch`.
